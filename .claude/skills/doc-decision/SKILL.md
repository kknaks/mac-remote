# /doc-decision — 프로젝트 계획 및 의사결정 문서 작성

## 읽어야 할 파일 (이것만 읽는다)

1. `doc/templates/Decision.tpl.md` — 템플릿
2. `doc/Decision.md` — 기존 문서가 있으면 (업데이트 시)

## 만들어야 할 파일

- `doc/Decision.md`

---

## 작성 규칙

1. 템플릿의 모든 섹션을 채운다. 빈 섹션을 남기지 않는다.
2. Project Overview는 사용자의 입력을 기반으로 작성한다. 추측하지 않는다.
3. ADR은 번호를 순차 부여한다 (ADR-001, ADR-002, …).
4. ADR 상태는 반드시 Proposed / Accepted / Deprecated / Superseded 중 하나다.
5. 기술 선택 요약 테이블은 "근거" 열을 반드시 채운다 — 선택 이유가 없는 기술 선택은 기록하지 않는다.
6. 핵심 제약은 체크박스 리스트로 작성한다. 프로젝트 진행 중 제약이 해소되면 체크한다.

## 예제

### Project Overview 예시

```markdown
| 항목 | 내용 |
|------|------|
| 프로젝트명 | 매크로 키보드 |
| 한줄 요약 | iPhone을 리모컨으로 써서 Mac의 창 전환 + 단축키 매크로 전송 |
| 시작일 | 2026-05-24 |
| 상태 | Active |

### Why — 이 프로젝트를 하는 이유

> Mac에서 여러 창을 전환할 때 키보드/트랙패드를 쓰기 번거롭다.
> iPhone을 물리 리모컨처럼 써서 한 탭에 원하는 창으로 이동하고 싶다.

### 핵심 제약

- [ ] LAN 전용 (인터넷 경유 불가)
- [ ] 화면 캡처/썸네일 금지 (앱 아이콘만 사용)
- [ ] iOS 앱 단독 동작 불가 (Mac 헬퍼 필수)
```

### ADR 예시

```markdown
### ADR-001: WebSocket을 통신 프로토콜로 선택

| 항목 | 내용 |
|------|------|
| 날짜 | 2026-05-24 |
| 상태 | Accepted |
| 맥락 | iOS ↔ Mac 간 실시간 양방향 통신이 필요하다. |
| 결정 | WebSocket (JSON payload)을 사용한다. |
| 근거 | HTTP 폴링 대비 지연이 낮고, 서버→클라이언트 push가 자연스럽다. Bonjour도 고려했으나 구현 복잡도 대비 이점이 적다. |
| 영향 | Mac 헬퍼가 WebSocket 서버를 내장해야 한다. |
```

## 해야 하는 것 (DO)

- 사용자에게 프로젝트의 목적, 제약, 기술 선택에 대해 질문한다.
- 대안을 비교한 근거를 ADR에 명시한다.
- 새 ADR을 추가할 때 기존 ADR과 충돌하는지 확인한다.
- 충돌하는 기존 ADR이 있으면 상태를 Superseded로 변경하고 새 ADR 번호를 기록한다.

## 하지 말아야 할 것 (DON'T)

- Decision.md 이외의 문서를 수정하지 않는다.
- 사용자가 말하지 않은 기술 선택을 임의로 추가하지 않는다.
- ADR에 구현 상세를 쓰지 않는다 — "무엇을, 왜" 까지만. "어떻게"는 Spec의 영역이다.
- 템플릿의 구조(섹션 순서, 테이블 열)를 변경하지 않는다.
